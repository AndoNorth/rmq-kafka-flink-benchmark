The one idea

same in Go and Python
A topic is cut into partitions. Producers may write to any partition. Each partition is read by exactly one consumer in a group. So the partition count is the ceiling on useful consumers, and the producer count is free.
  1. Producers do not own partitions. Each message carries a key (the message uuid). The client hashes the key and picks the partition, so every producer writes to all 4 partitions.
  2. Consumers do own partitions. The broker hands each partition to one member of the consumer group. Adding a consumer triggers a rebalance that moves some partitions to it.
  3. Go and Python differ only inside one process. Go can use several cores in one process. Python code in one process uses one core. To use more cores in Python you add processes, which here means containers.

consumer side

Consumers: one per partition, at most

observed

Question this answers: how do 4 consumers split 4 partitions, and what happens with 1 or 5?

Worked arithmetic with the real numbers
  1. Into the topic: 2 producers x about 10.2k msg/s = about 20.5k msg/s.
  2. Per partition: 20.5k / 4 partitions = about 5.1k msg/s arriving on each.
  3. Per consumer, 4 consumers: each owns one partition, so each must read about 5.1k msg/s. Measured: 5146, 5134, 5113 and 5062 msg/s.
  4. Per consumer, if there were only 2: each would own 2 partitions and need about 10.2k msg/s. A Python consumer capped at 0.5 CPU is the bottleneck here, so this is where the lag comes from.

Both join the group benchmark-consumers, so a Go consumer and a Python consumer can share partitions in the same group. Scaling is the same command: --scale redpanda-consumer=4.

Correction to what I said earlier

  • I said the lag was falling after scaling up. That was two samples. The later snapshot showed lag rising to about 82k, so 4 Python consumers at 0.5 CPU only roughly matched 2 producers running flat out.
  • Consumers beyond the partition count add nothing. To go faster than 4 consumers you need more partitions.

Reproduce it

commands
# monitoring first, then the Python stack at 2 producers and 4 consumers
docker compose -f docker-compose-monitoring.yml up -d
docker compose -f docker-compose-cadvisor-standard.yml up -d
docker compose -f docker-compose-redpanda.yml -f docker-compose-redpanda-py.yml up -d --build \
  --scale redpanda-producer=2 --scale redpanda-consumer=4

# who owns which partition
docker compose -f docker-compose-redpanda.yml exec redpanda rpk group describe benchmark-consumers

# stop, without --remove-orphans (it also removes monitoring)
docker compose -f docker-compose-redpanda.yml -f docker-compose-redpanda-py.yml down -v

Swap docker-compose-redpanda-py.yml for nothing to run the Go images at the same scale and compare. Use --build when you switch.
